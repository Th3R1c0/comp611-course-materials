[AA-0] Symbol key

n = size of the input

n is just "how much stuff the algorithm is given". Sorting a list of 1,000 numbers means n = 1,000. Everything else is described in terms of n so we can ask "what happens as n gets bigger?"

T(n) or f(n) = number of steps for an input of size n

Read the brackets as "for". T(n) means "the time (number of steps) for an input of size n". It's a little formula you plug n into.

T(n) = 2n + 1 → for n = 10: 2×10 + 1 = 21 steps

n² = n×n · n³ = n×n×n · 2ⁿ = 2×2×…×2 (n times)

The small raised number says how many times to multiply. These grow at very different speeds:

n = 10: n² = 100, n³ = 1,000, 2ⁿ = 1,024
n = 20: n² = 400, n³ = 8,000, 2ⁿ ≈ 1,000,000

log n = how many times you can halve n before reaching 1

8 → 4 → 2 → 1 is 3 halvings, so log 8 = 3. A million only takes about 20 halvings, so log n grows very slowly. You'll see a small number written under it, like log₂ or log₁₀. That's the "base", and in this course it never changes the answer.

n log n = n multiplied by log n

n = 8: 8 × 3 = 24

It sits between n and n²: a bit more than linear, much less than squared.

≤ at most · ≥ at least · c, n₀ = numbers we get to pick

In the Big-O definitions, c is a fixed multiplier (like 10) and n₀ (say "n-nought") is the starting point, the value of n from which the rule must hold. You choose them yourself to make the inequality true.

[AA-1] RAM model: how time is measured

Running time = number of elementary operations, not seconds

Timing with a stopwatch depends on the laptop, language and what else is running. So instead we count basic actions the algorithm does. Each counts as 1 step. That count is the same on any machine.

Elementary op = + − × ÷ %, compare (== != < >), assign, read/write A[i], return

A[i] means "the item at position i in the list A". "Assign" means storing a value, like x = 5. The model assumes reaching any memory spot takes the same 1 step.

Worst case = slowest input of size n · best = fastest · average = typical

Two lists of the same length can take different times. Searching for a name that's first in the list is instant; one that isn't there means checking everything. The worst case is the guarantee people care about most.

Space = most memory used at one moment; count only extra memory (not the input)

If an algorithm just uses a couple of counters (i, j) no matter how big the list is, its extra space is constant, written Θ(1).

[AA-2] O, Ω, Θ: comparing growth

O (Big-O) = ceiling: f grows no faster than g. f(n) ≤ c·g(n) once n ≥ n₀

f is your algorithm's step count. g is a simple shape like n². "f is O(n²)" means: past some point, your step count always stays under some fixed multiple of n².

A ceiling can be loose. "5n − 2 is O(n²)" is true, the same way "I'm under 3 metres tall" is true.

Ω (Big-Omega) = floor: f grows at least as fast as g. f(n) ≥ c·g(n)

The same idea flipped. Past some point, your step count is always above some fixed multiple of g.

Θ (Big-Theta) = both: f grows exactly like g. Only exists if ceiling = floor

If the ceiling and the floor are the same shape (both n², say), the growth is pinned down exactly: Θ(n²). If they differ, like insertion sort's n² worst and n best, there's no single Θ that covers every input.

"Tight bound" in a question = they want Θ = the biggest term

Multiple choice often asks for the "tight asymptotic bound". That's Θ, and you find it with [AA-4]: keep the fastest-growing piece and drop its number.

[AA-3] Proving O with c and n₀ (recipe)

Upper (O): c = add the positive numbers in front, n₀ = 1. 3n²+5n+2 ≤ 10n²

When n is 1 or more, n is never bigger than n², and 1 is never bigger than n². So you can swap each smaller piece for n² and only make the total bigger:

3n² + 5n + 2 ≤ 3n² + 5n² + 2n² = 10n²

So c = 10 and n₀ = 1 work.

Lower (Ω): c = number in front of the biggest term, n₀ = 1. 3n²+5n+2 ≥ 3n²

The extra pieces (5n and 2) are positive, so removing them can only make it smaller. So the whole thing is at least 3n².

Checking an option (c, n₀): plug in n = n₀ and a bigger n. c must be ≥ the leading number

Example: f(n) = 2n² + 3n + 1, option c = 6, n₀ = 1. At n = 1: f = 6, and 6 × 1² = 6. 6 ≤ 6 ✓. At n = 10: f = 231, 6 × 100 = 600 ✓.

A c smaller than the leading number (here 2) can never work for big n, because the n² part alone already beats it.

Minus sign? Pick n₀ where it's small: n²/2 − 5n ≥ n²/4 once n ≥ 20

Taking something away can make the floor fail for small n. Find where the subtracted part is at most half the big part. At n = 20, 5n = 100 and n²/4 = 100, so from there on it holds.

[AA-4] Simplifying to the growth class

Keep only the biggest term: 7n³ + 200n² + 9 → Θ(n³)

For large n the biggest power swamps the rest. At n = 1,000: 7n³ = 7 billion, 200n² = 200 million. The n³ part wins and keeps winning.

Drop the number in front: 100n → Θ(n) · log base doesn't matter

Doubling n doubles 100n just like it doubles n, so they grow the same way. The number only changes the speed on a given machine, not the shape.

Trap: 5n − 2 is O(n²) TRUE, but Θ(n²) FALSE (it's Θ(n))

O is just a ceiling, so a high ceiling is allowed. Θ must be exact, so it has to be n.

[AA-5] Growth order & the doubling test

1 < log n < n < n log n < n² < n³ < 2ⁿ < n!

Slowest growing on the left, fastest on the right. For n = 1,000: log n ≈ 10, n log n ≈ 10,000, n² = 1,000,000, and 2ⁿ is too big to write. n! (n factorial) is 1×2×3×…×n.

Timing table: when n doubles, time × 1 → log n · 2 → n · ~2.1 → n log n · 4 → n² · 8 → n³

If the work is n², doubling n gives (2n)² = 4n², so 4 times the time. If it's n³, it's 2×2×2 = 8 times. So divide each time by the one before it and match the ratio.

0.5 s → 1.0 s → 2.0 s : ratio 2 → Θ(n)

2ⁿ: adding just 1 to n doubles the time

That's why exponential algorithms become hopeless so fast.

[AA-6] Counting steps from pseudocode

Recipe: count how many times the innermost line runs, then simplify ([AA-4])

Pseudocode is code written in plain-ish English. The line inside the deepest loop runs the most, so it decides the growth.

One loop 1 to n → n · two nested loops to n → n×n = Θ(n²) · three → Θ(n³)

A loop "for i = 1 to n" repeats its body n times. Putting a loop inside a loop multiplies: n times round the outer, n times round the inner each time.

Inner loop starts after outer (for j = i+1 to n) → n(n−1)/2 → still Θ(n²)

This checks every pair once. With n = 5: 4 + 3 + 2 + 1 = 10 pairs, and 5 × 4 ÷ 2 = 10. It's about half of n², and halving doesn't change the class.

Loop that halves n (or doubles i) → log n · inside an n-loop → n log n

"while n > 1: n = n / 2" runs log n times by definition of log ([AA-0]). Put it inside a normal loop of n and it's n × log n.

Shortcut: 1 + 2 + … + n = n(n+1)/2

Pair the first with the last: 1+n, 2+(n−1), … each pair adds to n+1, and there are n/2 pairs. Example: 1+2+…+10 = 10 × 11 ÷ 2 = 55.

[AA-7] Best & worst cases to know

AlgorithmBestWorst
Linear searchΘ(1)Θ(n)
Insertion sortΘ(n)Θ(n²)
Merge sortΘ(n log n)Θ(n log n)
Binary searchΘ(1)Θ(log n)
Selection / bubbleΘ(n²)Θ(n²)
Linear search: best = target first, worst = not there (2n + 1 steps)

It checks items one by one. If the target is first, it's done in 1 check. If it's missing, it checks all n items (n loop steps + n comparisons + 1 return = 2n + 1).

Insertion sort: best = already sorted, worst = reverse sorted, n(n−1)/2 shifts

It takes each item and slides it left into place, like sorting cards in your hand. If the list is already sorted, nothing slides. If it's backwards, every item slides all the way: 1 + 2 + … + (n−1).

Merge sort = n log n on every input · binary search halves a sorted list each step

Merge sort always splits and merges the same way, so the input order doesn't matter. Binary search looks at the middle, throws away the half that can't contain the target, and repeats, so it takes log n steps.

Early return in a loop → no single Θ: say O(worst) and Ω(best)

If the code can stop early, the time depends on the actual values, not just n. Then the honest answer is "at most the worst, at least the best". Remove the early return and it always runs to the end, so one Θ works.

[AA-8] Fibonacci case study

Naive recursion: exponential (~1.618ⁿ, O(2ⁿ)) · memo / loop: O(n) · matrix power: O(log n)

Fibonacci: each number is the sum of the two before (0, 1, 1, 2, 3, 5, 8 …). The naive version recalculates the same numbers over and over, so the work explodes. Storing answers in a list ("memoisation") or just looping fixes that: one step per number. A matrix trick gets it down to log n.

[AA-9] Traps & definitions

"O(n²) means quadratic on every input" → FALSE

O is only a ceiling. Insertion sort is O(n²) but runs in linear time on a list that's already sorted.

Seconds on one laptop ≠ complexity

Three problems: it depends on the machine, one measurement can't show how time grows, and you don't know if it was a best or worst case input.

Algorithm = finite, well-defined steps from input → output

Its five properties: well-defined inputs, well-defined outputs, finiteness (it stops), definiteness (each step is unambiguous), effectiveness (each step is simple enough to actually do).
